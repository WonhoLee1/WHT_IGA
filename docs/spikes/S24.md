## 정정 (2026-11-14, 통합 담당 — REVIEW_P0_P1 §1 #7, review_v2.1_additions R1)

결론의 "MechanicalExplicitStrategy를 MPC와 직접 결합할 수 없음(비변분적 질량 전달)"은 과장이다. 아래와 같이 정정한다.

- 잔차: `PreComputeExplicitConstraintConstribution`이 slave 잔차를 master += Tᵀ·f_slave로 옮긴다. Q1 실측 `-5.0`이 이를 보여 준다. 이 처리는 맞다.
- 질량: `PreComputeExplicitConstraintMassAndInertia`는 m_master += Σ_i T_ij·m_i 이다.
  - extension 연산자처럼 T의 행합이 1이면(분할단위성), 이 값은 대각 M에 대한 **TᵀMT의 row-sum lumping과 같다.** 변분 질량의 lumping 근사이지 비변분적인 처리가 아니다.
  - Q1의 1.0 대 1.5 불일치는 행합이 2인 T(u_s = 2u_m)를 썼기 때문이다. extension 상황을 대표하지 않는다.
  - 총 질량 6.0에는 slave 질량이 포함돼 있다. slave 자유도는 매 단계 복원되므로 적분에 쓰이지 않는다.
- 실제 문제: extension 가중치가 음수일 수 있다(p=1 예 T = [−1, 2]). 이 경우 row-sum 질량이 0이나 음수가 될 수 있다(Q1 실측 2.776e-17). 그러면 중앙차분 안정성과 Δt_crit가 깨진다.
- 미시험(명시): `Initialize()` 후 NODAL_MASS를 Python에서 계산한 HRZ(TᵀM_cT) 대각 값으로 덮어쓰고 `MechanicalExplicitStrategy`를 그대로 쓰는 혼합안은 시험하지 않았다. 이 혼합안이 통과하면 Python 루프 없이 Kratos explicit 경로를 쓸 수 있다. Phase 6 착수 전 spike로 확인한다.
- 현재 권장: 음수 가중치가 없는 경우(무절단, 또는 extension이 없는 셀)에는 Kratos 경로를 쓰고, extension이 있는 경우에는 Q2의 Python 루프(HRZ)를 쓴다. 혼합안 결과를 보고 다시 판단한다.
